MARC 21 Format for Bibliographic Data (Z39.2)
=============================================

Added to :doc:`Standards </sources/standards/index>` on 2024-09-01.

.. evidence-from:: marc21

.. evidence:: codec.leader.Leader
   :source: marc21
   :title: MARC 21 Format for Bibliographic Data (Z39.2)
   :lens: rfc
   :source-kind: standard
   :date: 2024-09-01
   :section: §4.2

   codec.leader.Leader conforms to MARC 21 §4.2: its fixed 24-octet width is dictated by the standard, not the domain.

   .. evidence-quote::

      It consists of 24 octets (character positions 00-23) and is the only field of fixed length.

.. evidence:: codec.leader.Leader
   :source: marc21
   :title: MARC 21 Format for Bibliographic Data (Z39.2)
   :lens: rfc
   :source-kind: standard
   :date: 2024-09-01
   :section: §4.2

   codec.leader.Leader.record_status implements MARC 21 §4.2's position-05 status code (n new, c corrected, d deleted).

   .. evidence-quote::

      Character position 05 contains the record status: a single character, where `n` denotes a new record, `c` a corrected or revised record, and `d` a deleted record.

.. evidence:: codec.record.Marc21Record
   :source: marc21
   :title: MARC 21 Format for Bibliographic Data (Z39.2)
   :lens: rfc
   :source-kind: standard
   :date: 2024-09-01
   :section: §5

   codec.record.Marc21Record conforms to MARC 21 §5: it keeps fields in ascending tag order because the transmission format requires it.

   .. evidence-quote::

      Variable fields are transmitted in ascending tag order, and each variable field is closed by a field terminator.

.. evidence:: codec.record.Marc21Record
   :source: marc21
   :title: MARC 21 Format for Bibliographic Data (Z39.2)
   :lens: rfc
   :source-kind: standard
   :date: 2024-09-01
   :section: §4.3

   codec.record.Marc21Record's directory handling conforms to MARC 21 §4.3: fixed 12-octet entries, in ascending tag order.

   .. evidence-quote::

      Each entry is a fixed 12 octets and gives the tag, length, and starting character position of one variable field. Entries appear in ascending order of the tags they point to.

*A party with a stake in the library's outcomes who does not operate the
loans system.* The counterpart root to ``user``: where a user has hands on
the system — issuing loans or borrowing — a stakeholder is served through
it at one remove, their interest mediated by the users and the collection
rather than by any workflow they run themselves.

There is 1 type of Stakeholder:

* :doc:`Teacher </personas/teacher>`
=== canonical/persona.teacher.rst ===
.. GENERATED by disco_agent.usecases.canonical.render_canonical — do not edit by hand.
.. Source of truth: discovery/canonical/<namespace>.toml.

*A local school teacher with a stake in the library, served entirely
through the pupils they teach.* A teacher holds no card and issues no
loans — they never touch the loans system — but their pupils are
:doc:`borrowers </personas/borrower>` who visit each week, and the teacher
recommends acquisitions on the strength of what gets reluctant readers
reading at home (Miss Jones of Class 2B asked the library to stock Frank
Murr's "What a Mess" books for exactly this reason). The interest is real
but indirect: it runs through the student borrowers and through the
collection's reading-engagement, never through an operational workflow.

A Teacher is a type of :doc:`Stakeholder </personas/stakeholder>`.
